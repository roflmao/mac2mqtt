# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository.

## What this project is

mac2mqtt is a small Go daemon that runs on macOS, publishes system status
(volume, battery, display, user activity, Wi-Fi, temperatures, ...) to an
MQTT broker, and accepts commands (volume, mute, sleep, shutdown, reboot)
back over MQTT. It publishes Home Assistant MQTT auto-discovery messages so
every sensor appears automatically.

## Layout

| Path | Purpose |
|------|---------|
| `main.go` | The entire application: config, MQTT client, sensors, commands, discovery, auto-update, main loop |
| `main_test.go` | Unit tests for pure functions (parsers, threshold logic, config defaults) |
| `mac2mqtt.yaml.example` | Documented example config; every config key must appear here |
| `README.md` | User documentation, including the metrics table and per-topic reference |
| `TODO.md` | Feature roadmap; tick items off when implemented |
| `CHANGELOG.md` | Generated by CI from commit subjects; do not edit by hand |
| `install.sh` | Installs the binary as a LaunchDaemon (root) or LaunchAgent (user) |
| `com.bessarabov.mac2mqtt.*.plist.template` | launchd templates used by `install.sh` |
| `.github/workflows/release.yml` | Release pipeline, triggered by every push to `master` |
| `.github/scripts/update_changelog.py` | Builds the CHANGELOG entry from `git log` |

## Build and test

```bash
go build -o mac2mqtt .     # cross-compiles fine on Linux; macOS tools are only exec'd at runtime
go vet ./...
go test ./...
```

Always run vet, test and build before claiming work is done. `gofmt` reports
pre-existing alignment nits in `main.go`; format the code you touch, but do
not reformat the whole file in an unrelated change.

To run locally without a broker, set `dry_run: true` in `mac2mqtt.yaml`.
MQTT publishes are then logged instead of sent. On a non-macOS host the
macOS command-line tools are missing, so most sensors publish nothing.

## How sensors are structured

All sensors follow the same pattern in `main.go`. When adding one, do all of
these in the same change:

1. **Getter**: `getFoo()` runs a macOS tool (`ioreg`, `pmset`, `osascript`,
   `sysctl`, `system_profiler`, ...) and parses its output. Put the parsing in
   a separate pure function (e.g. `parseHIDIdleTime(output string)`) so it can
   be unit tested without macOS. Use `tryGetCommandOutput` and handle errors;
   `getCommandOutput` calls `log.Fatal` on failure and should only be used for
   commands that must exist.
2. **Publisher**: `updateFoo(client)` publishes to
   `mac2mqtt/HOSTNAME/status/foo` via `publishMQTT` and waits on the token.
   Use `getTopicPrefix()` for the prefix.
3. **Discovery**: add a config map in `publishDiscoveryMessages` with
   `unique_id` `mac2mqtt_<hostname>_foo`, the availability block, and the
   shared `device`. Pick an appropriate Home Assistant `device_class`,
   `state_class` and `unit_of_measurement`.
4. **Initial publish**: call `updateFoo(client)` in the on-connect handler so
   the value is published immediately.
5. **Schedule**: add it to the 2-second ticker (cheap commands) or the
   60-second ticker (expensive or slow-changing data) in `main()`.
6. **Config** (if needed): add a field to `config`, a getter with a sane
   default, document it in `mac2mqtt.yaml.example` and the README
   configuration list.
7. **Docs**: add a row to the metrics table in README.md and a section under
   "Status Topics". Tick the item in TODO.md.
8. **Tests**: cover the parser and any threshold or default logic in
   `main_test.go`.

Commands follow the same shape: handle the topic in `listen`, add a
`commandFoo()` function, add a discovery entry (`button`, `switch`, ...),
and document it under "Command Topics".

Keep existing topic names and payload formats stable; Home Assistant
installs depend on them.

## Permissions and run modes

The daemon can run as root (LaunchDaemon) or as the logged-in user
(LaunchAgent). CPU temperature and fan speed need root (`powermetrics`).
Prefer data sources that work without extra permissions or TCC prompts.
Note any required permission in README.md.

## Git workflow

- Work on a feature branch (`feature/<name>` or `fix/<name>`), open a PR
  against `master`, merge with a merge commit.
- **Every push to `master` is a release.** CI auto-increments the patch
  version, prepends a CHANGELOG entry built from the non-merge commit
  subjects since the previous tag, builds darwin/linux binaries, and creates
  a GitHub release. Push to `master` only when you intend to release.
- Because commit subjects become CHANGELOG bullets, write them as short,
  user-facing, imperative sentences ("Add idle time sensor", "Fix rollback
  path in root mode").
- Do not add AI co-author or "generated by" attribution to commit messages.
- To release a specific version manually, tag the commit `vX.Y.Z` before
  pushing; CI then skips its own auto-increment.
